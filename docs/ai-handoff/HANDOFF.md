# Sonix Player (форк rekkod-mod): как велась доработка интерфейса

Документ для того, кто продолжает работу (человек или другая модель). Здесь описано, как работа была организована процессно и технически, на что обращалось внимание, где лежат материалы и что осталось. Читать до того, как трогать код.

Состояние на момент передачи: ветка `sonix-r1` форка `Rekkod-Tree/sonix-player-rekkod-mod`, HEAD `282e366`. На устройстве у владельца стоит образ **1.3.0-beta3** (Sonix UI 2.0, Яндекс Музыка, Звук на моке). Номер версии в `system-info.json` в ветке остаётся 1.2.5: беты собирались с временно поднятой версией.

---

## 1. Контекст

**Устройство.** HiBy R1 (основное), также R3 Pro II.
- Процессор Ingenic X1600: одно ядро MIPS, которое одновременно декодирует звук и рисует интерфейс.
- 64 МБ ОЗУ, во время работы свободно около 10 МБ.
- Экран R1 480×800, у R3 Pro II 480×720. Тачскрин и четыре кнопки справа (громкость +/−, играть, далее). Кнопки «назад» нет.
- BlueZ 5.54 и bluealsa 4.3.1. Владелец слушает Soundcore Space One Pro по LDAC: Bluetooth — основной сценарий, не второстепенный.

**Интерфейс.** LVGL 9.6, цвет RGB565, два полноэкранных буфера, цель 60 кадров/с. Шрифты MiSans через FreeType, рисуются по требованию.

**Репозиторий.**
- `sonix-player/` — код плеера на C.
- `sonix-packer/` — сборщик образа `r1.upt` и ресурсы:
  - `assets/R1/usr/resource/...` и `assets/R3PII/...`;
  - языковые .ini;
  - версия в `assets/R1/usr/resource/sonix/components/system-info.json`.
- `CHANGELOG-rekkod.md` — подробный журнал отличий форка от upstream по версиям. Его ведём при каждом релизе.

**Ветки и политика.**
- Вся работа идёт в `sonix-r1`. Upstream-код автору не предлагаем.
- Сервис Звук существует только в форке и только под флагом сборки `SONIX_ZVUK`.
- Вход в Звук — **только** через файл с токеном на карте:
  - токен сохраняется с правами 0600, файл на карте после импорта удаляется;
  - QR-кода и страницы вставки токена в SonixLink нет и не будет.

**Секреты.** Файлы `streaming-keys.key` / `streaming-keys.ini` и любые токены **никогда** не коммитить. Если владелец присылает архив с папкой `secrets` — не копировать её в рабочие деревья.

## 2. Сборка, упаковка, проверка, доставка

### Сборка

```sh
cd sonix-player
make host -j2      # SDL-эмулятор (x86); первый раз клонирует LVGL 9.6.0
make target -j2 ROCKBOX_TOOLCHAIN_DIR=<путь>/rockbox-toolchain   # бинарник для устройства
```

**Тулчейн.** rockboxdev `mipsel-rockbox-linux-gnu`, sysroot с glibc 2.27, alsa-lib, dbus, glib.
- На устройстве glibc старее, поэтому `make target` обязан закончиться строкой `check-abi: no symbol beyond glibc 2.22`.
- Новые функции libc сверх 2.22 нельзя (см. `glibc_compat.h`).
- Для target-сборки рядом с исходниками нужны собранные статические `freetype-target/` и `audio-target/`.

**Предупреждения.** Host-сборка должна быть без предупреждений в тех файлах, которые ты трогал.

### Упаковка

`sonix-packer/sonix_firmware_packer.sh` собирает `r1.upt`: ISO, внутри которого squashfs разрезан на части с md5. Скрипт берёт стоковый `r1_original.upt`, бинарник `sonix_player`, `sonix_launch` и `assets/R1`. Подробности — в шапке скрипта.

### Проверка образа перед отдачей (обязательно, каждый раз)

1. Распаковать ISO через `bsdtar`.
2. Склеить части squashfs и сверить md5 с тем, что записано в образе.
3. Распаковать squashfs через `unsquashfs` и сравнить бинарник побайтно с собранным (`cmp`).
4. Прочитать версию из `system-info.json` внутри образа и убедиться, что она нужная.

### Доставка

Образ кладётся владельцу в `D:\Projects\Mediateka\firmware\<версия>\r1.upt`, рядом `release-notes.md`. Владелец пишет на 4pda, поэтому заметки короткие, на русском, с разделом «Известные проблемы».

Шла цепочка через мост на компьютер владельца:
1. Разрезать образ на части по 20 МБ.
2. Записать части в папку на компьютере.
3. Склеить там через `copy /b`.
4. Проверить SHA256 через `certutil` и сверить с хешем на стороне сборки.

### Версии

- Беты: временно поднять версию в `system-info.json`, собрать образ, откатить файл через `git checkout`.
- Релиз: коммит с версией плюс раздел в `CHANGELOG-rekkod.md`.

## 3. Эмулятор: как проверять интерфейс без устройства

Почти всё проверялось в эмуляторе. Это главный инструмент: любое изменение интерфейса подтверждается скриншотом.

### Запуск

- **Экран.** Безголовый X: `Xvfb :NN -screen 0 480x800x24`.
- **Скриншот:** `xwd -root -display :NN | convert xwd:- shot.png`. Затем на скриншот надо посмотреть глазами.
- **Ввод:**
  - касание — `xdotool mousemove X Y click 1`;
  - свайп — `mousedown`, `mousemove`, `mouseup`;
  - кнопки: `p` питание, `u`/`i` громкость, `b` `n` `m` транспорт.
- **Рабочий каталог** должен содержать `usr/resource`, скопированный из `sonix-packer/assets/R1/usr/resource`. Без него эмулятор падает в `vlimit_refresh` (NULL `sysinfo_model`).
- **Изоляция.** Плеер пишет базу в `/tmp/.local` и читает карту из `/mnt/sd_0`, поэтому каждый экземпляр запускается в своём mount-неймспейсе:

  ```sh
  unshare -m --propagation private sh -c \
    "mount --bind $T/dotlocal /tmp/.local && mount --bind $T/card /mnt/sd_0 && exec $T/sp_myname"
  ```

- **Имя бинарника.** Бинарник копируется под уникальным именем (не длиннее 15 символов) и останавливается только командой `pkill -x <имя>`. `pkill -f sonix_player_host` убивает чужие эмуляторы, а иногда и собственный shell.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `SONIX_PANEL=480x800` (или `480x720`) | Размер панели |
| `SONIX_SD_ROOT`, `SONIX_CONFIG` | Карта и `device_config.ini` |
| `SONIX_NO_MOUNT=1`, `SONIX_NO_SYSSERVER=1` | Без монтирования и системного сервера |
| `SONIX_LOG` | Путь к логу |
| `SONIX_SXDEMO=1` | Демо-страница компонентов UI 2.0 |
| `SONIX_WIFI_FAKE`, `SONIX_BT_FAKE` | Имитация Wi-Fi и Bluetooth |
| `SONIX_FAKE_OFFLINE=<файл>` | Офлайн, пока файл существует |
| `SONIX_PERF` | Счётчики производительности; `kill -USR2 <pid>` пишет отчёт |
| `SONIX_TEST_RESAMPLE` | Проверка ресемплера |

### Тестовые данные

**Демо-карта.** Альбомы с правильными тегами и сгенерированными обложками:
- разные годы, названия подобраны так, что порядок по алфавиту не совпадает с хронологическим;
- сборник с `COMPILATION=1` без albumartist;
- кириллица («Кино»);
- файл без тегов;
- файл с ReplayGain −8 дБ.

Кириллицу в теги писать так: `LC_ALL=C.UTF-8 metaflac --no-utf8-convert ...`, иначе вместо букв получаются `#`.

**Готовый `device_config.ini`.** Приветствие пройдено, интерфейс на русском. Копировать его, а не проходить первый запуск заново.

### Моки сервисов (`sonix-player/tools/`)

- `yandex_mock.py`, `zvuk_mock.py`, мок Subsonic.
- Fault-proxy с режимами `ok` / `slow` / `401` / `403` / `404` / `503` / `reset` / `stall`. Через него проверяются понятные ошибки стриминга и кнопка «Повторить».
- У каждого агента свои порты; в `device_config.ini` прописываются `base_url` и `server` мока.

## 4. Процесс: как организовывалась работа

### 4.1. Волны

Работа шла волнами. Одна волна — один набор задач от владельца, затем бета или релиз на устройство.

1. **Разбор запроса.** Сначала чтение кода и логов устройства, если владелец их присылал: `sonix_player.log`, `bluetooth.log`, `library.db`. Затем разбиение на независимые направления. Если вопрос открыт и ошибка дорога, один вопрос владельцу. Иначе консервативное решение, записанное в коммит и в отчёт.
2. **Оркестратор и параллельные агенты.**
   - Каждому направлению свой агент, свой `git worktree` и своя ветка (`r125-queue`, `r131-zvuk` и т. п.).
   - У агента свой номер дисплея Xvfb, свой временный каталог, свои порты моков.
   - Сборка `-j1` или `-j2`: на машине 2 ядра на всех.
3. **Владение файлами.** До запуска агентов файлы распределяются так, чтобы направления не пересекались. Пример из 1.2.5:
   - очередь → `player`, `trackmenu`, меню экрана воспроизведения, кнопки;
   - стриминг → общий слой и новые «Загрузки»;
   - Яндекс → `yandex*.c`;
   - UI → общие виджеты;
   - аудио → `audio.c`, ресемплер, DSD, ввод.

   Чужой файл правится минимально и обязательно упоминается в отчёте.
4. **Общие правила** лежат в одном файле, который читает каждый агент (`WAVE_NOTES.md`, копия в этой папке). В нём:
   - ограничения платформы;
   - стиль кода;
   - правила переводов;
   - как запускать эмулятор;
   - уроки прошлых волн;
   - база текущей волны.

   После каждой волны туда дописывался раздел.
5. **Структура задания агенту:**
   - база (коммит);
   - worktree, дисплей, порты;
   - список пунктов с ожидаемым поведением;
   - чьи это файлы;
   - что прочитать сначала;
   - как проверить в эмуляторе;
   - формат коммита и трейлеры;
   - формат финального отчёта: по каждому пункту «сделано / частично / нет», какие файлы, как проверено (пути к скриншотам), риски, что проверить на устройстве.
6. **Наблюдение.**
   - Агенты могли молча остановиться: лимиты сессии, обрывы.
   - Прогресс отслеживался по времени изменения файлов в worktree (сортировка по epoch) и по коммитам.
   - Остановившийся агент перезапускался заново с запиской: что уже сделано (по `git log` и диффу) и что осталось.
7. **Слияние.**
   - Порядок слияния планировался заранее: сначала фундамент (общие модули), потом экраны.
   - Конфликты в языковых .ini разрешались объединением обеих сторон с проверкой на дубли ключей.
   - Конфликты в коде — по смыслу, с выбором поведения, которое задумано в дизайне. Например, `topbar.c`: при воспроизведении показывается ❚❚, как решил QA.
8. **Швы после слияния.** Когда два агента сделали одно и то же по-разному, после слияния оставлялся один механизм:
   - два fan-out тона обложки → `covertonefan`;
   - два API отмены добавления в очередь → `queueundo.h`;
   - провайдер тона палитры подключался в `main.c` после `covertone_ui_init()`.
9. **Дымовой тест** в эмуляторе по главным экранам. Затем бета-версия, упаковка, проверка образа, доставка.
10. **Документация после релиза:**
    - раздел в `CHANGELOG-rekkod.md`;
    - `release-notes.md` для 4pda;
    - заметка в проекте владельца.

### 4.2. Отдельная волна QA и отдельная волна производительности

После крупных изменений (UI 2.0) шла волна, где один агент только ищет и чинит мелкие косяки, сверяя каждый экран с макетом и с прежним поведением. Результат — таблица «коммит → что починено» и список «осталось» с оценкой серьёзности (см. `QA-1.3.0.md`).

Второй агент в это время меряет:
- CPU в простое;
- частоту таймеров;
- перерисовки при выключенном экране;
- стоимость градиентов.

Результат — `PERF-1.3.0.md`. Пример находки: таймер простоя срабатывал 89,6 раза/с, после правки 17,4 раза/с.

### 4.3. Коммиты

Один коммит на одну возможность, в стиле автора upstream:
- тема коммита — короткий список возможностей;
- тело сгруппировано по областям, пишется понятной пользователю прозой.

Каждый коммит заканчивается трейлерами:

```
Co-Authored-By: <модель>
Claude-Session: <ссылка>
```

Если продолжает другая модель, трейлеры ставятся свои.

### 4.4. Взаимодействие с владельцем

- Владелец пишет по-русски коротко и часто в стиле «Продолжаем» / «Как успехи?». Ему нужен результат, файл образа и короткий список, а не рассказ о процессе.
- Когда он не на связи, решения принимаются консервативно и документируются.
- Изменённые значения по умолчанию действуют **только** если ключ в конфиге ещё не задан. Нельзя переопределять то, что пользователь уже выбрал.
- Указание, повторявшееся в каждой волне: **сохранять каждую существующую функцию** (ничего не терять молча) и по ходу чинить мелкие недочёты, перечисляя их в отчёте.

## 5. Цепочка «дизайн → код»

1. **Дизайн-система снята с кода.** Токены (цвета, отступы, размеры шрифтов, тайминги) взяты из исходников, плюс 32 скриншота из эмулятора и текстовое описание (`reference/sonix-ui-1.2.5-description.md`). Всё это владелец загрузил в Claude Design и переработал интерфейс там.
2. **Пакет от дизайна** (`handoff/`):
   - `README.md` — принципы, матрица жестов, модель очереди, экраны, компоненты, анимации, конвейер обложек, сопоставление иконок;
   - `sonix_ui_tokens.h` — все размеры, тайминги, пороги и цвета, включая OKLCH-палитру тона;
   - интерактивный прототип `prototype/Sonix UI 2.0.dc.html`.

   Это источник истины. Если код и README расходятся, верен README, кроме мест, где дизайн упирается в ограничения платформы (раздел 6).
3. **Рендер прототипа в картинки.** Скрипт на Playwright (`shoot.py`) открывает прототип и снимает каждый экран 480×800. React грузится локально (`npm pack` + перехват запросов), потому что CDN был недоступен. Клики делаются через `page.evaluate`. Эти PNG агенты кладут рядом со своими скриншотами и сравнивают.
4. **Фаза 1 — фундамент с зафиксированным API.** Сначала три агента сделали общие модули (`sx_*`, обложки, Яндекс). После слияния написан `PHASE1_API.md` — карта API, которую получали агенты фазы 2. Экраны строятся только на этих модулях, без своих велосипедов.
5. **Фаза 2 — экраны** (списки, плеер, сервисы, системные страницы) параллельно, на API фазы 1.
6. **Волна QA и производительности** (раздел 4.2), затем бета.
7. **UI 3.0.** Владелец сделал в Claude Design следующую итерацию (`Sonix UI 3.0.dc.html`). Импортировать её отсюда не удалось: нужна авторизация в дизайн-инструменте. Ждём экспорт (html + `support.js`). Порядок работы тот же: прочитать README и токены, отрендерить прототип, составить разницу с 2.0, сначала фундамент, потом экраны.

## 6. Технические принципы: на что обращалось внимание

### Производительность и батарея (главное)

- **Нулевая цена в простое.**
  - Новая возможность, которой не пользуются, не должна тратить ни CPU, ни память.
  - Никаких постоянных таймеров «на всякий случай».
  - Наблюдатели раз в секунду объединяются.
  - При выключенном экране ничего не рисуется.
- **Одно ядро.** Тяжёлое (сеть, разбор JSON, обложки, сканирование) — в рабочих потоках с низким приоритетом (`thread_be_low_priority`). Полноэкранная анимация конкурирует с декодером и может дать щелчок в звуке.
- **Поток LVGL один.** Только UI-поток трогает `lv_*`. Рабочие потоки возвращают результат через `gui_post()`. В заголовке каждого модуля описан контракт потоков.
- **Память.** Около 10 МБ свободно.
  - Длинные списки (тысячи треков в «Мне нравится») грузятся лениво, страницами: 8 байт на запись, детали пачками по 50, LRU на 12 страниц.
  - Строки списков переиспользуются: сеттеры `sx_row_*` не создают объектов.
  - Миниатюры обложек лежат в slot-файлах на карте, а не в ОЗУ.
- **Ограничения рендера:**
  - **нельзя:** живое размытие, тени (кроме ручки ползунка), анимации прозрачности, полноэкранные затемнения, перспектива, масштабирование картинок на лету;
  - **градиенты:** только как дизерированная полоса 1×H (RGB565, упорядоченный дизеринг 4×4), только на статичных экранах;
  - **переходы:** сдвиг MOVE 180 мс, без «пружин».
- **Обложки:**
  - 240 px нельзя декодировать на UI-потоке — только асинхронно;
  - 56 px допустимо;
  - `covertone_for_path` нельзя вызывать внутри колбэков библиотеки (взаимоблокировка на блокировке библиотеки).
- **Иконки** запекаются в каждом нужном размере (`tools/svg_to_lvgl.py`). Новый размер — новый битмап; иконки уже занимают около 4,2 МБ.
- **Шрифты.** Новый размер — новый растровый кеш. Добавлять только при реальной необходимости.

### Звук

Принцип владельца: **максимальное качество без лишней обработки.**
- Не ресемплировать, когда частота поддерживается напрямую.
- Ресемплер полифазный, с дизерингом.
- Строка цепочки (`sx_chain`: «LDAC 990 · 44.1 → 48 kHz») честно показывает, где есть преобразование, и подсвечивает несовпадение кодека.

### Совместимость и тексты

- **Все строки переводятся.** Каждая новая подпись — ключ во **всех 11** языковых .ini и в **обоих** наборах (R1 и R3PII), то есть 22 файла, с настоящим переводом.
  - Ключи ставятся сразу после комментария `; --- file.c` своего файла. Для нового файла — новая секция в конце.
  - Метки в статических инициализаторах `popover_item_t` должны быть статическими.
  - Ловушка: поиск ключа по значению. Ключ «Ещё» переименовал плитку в «Дополнительно».
- **Длинные строки.** Немецкий, французский, итальянский и испанский длиннее английского на 17–30 %. Каждая подпись либо помещается, либо имеет правило переноса или многоточия. Проверять на русском и на немецком.
- **Две высоты экрана.** Всё проверяется на 800 и на 720.
- **Тёмная и светлая тема**, шесть акцентов. Ничего не должно держаться на синем акценте:
  - на жёлтом и зелёном белый текст нечитаем — текст на акценте берёт его «чернила» (`on_accent`);
  - акцент как цвет текста затемняется до контраста не ниже 3:1.
- **Настройки** хранятся в существующих секциях конфига (`[library]`, `[music]`, `[bluetooth]`, ...). Новые значения по умолчанию действуют только для незаданных ключей (раздел 4.4).

### Ввод и жесты

- Переключатели срабатывают только по тапу (CLICKED), чтобы свайп страницы их не переключал.
- Долгое нажатие должно «съедать» отпускание, иначе получается лишний тап. На этом было несколько ошибок.
- Назад: свайп от левого края (22 px, порог 70 px). Плавающая кнопка ‹ не должна отключать жест.
- На R1 кнопки справа, работа одной рукой: важное должно быть в нижней половине, зоны касания не меньше 72 px.

### Стиль кода

- `.clang-format`: табы, ширина 4.
- Префиксы `модуль_глагол`.
- Британское написание (favourites, colour).
- Длинные комментарии объясняют **почему**.
- Код пишется в стиле окружающего.

## 8. Грабли (чтобы не наступать повторно)

- Эмулятор падает без `usr/resource` в рабочем каталоге.
- Общий `/tmp/.local` у параллельных эмуляторов портит базу. Нужна изоляция через `unshare`.
- `pkill -f` / `pkill sonix_player_host` убивает чужое. Только `pkill -x <уникальное имя>`.
- `metaflac` без `C.UTF-8 --no-utf8-convert` портит кириллицу.
- Генерация обложек с поворотом давала белые углы. Использовать `-sparse-color Barycentric`.
- **Один слот слушателя:** если модуль позволяет одного подписчика, второй агент молча вытеснит первого. Делать fan-out.
- **Одинаковые механизмы:** две параллельные реализации одного и того же после слияния — частая беда. Искать и объединять (очередь, перемешивание, тон обложки).
- **«Моя волна» переставала догружаться:**
  - задание перезаписывалось и не было повторов;
  - позже действия «Следующим» / «В конец» засчитывались волной как пропуск трека.
- Синхронизация лайков на `SCHED_IDLE` не успевала. Скачивание — на низком приоритете, а не на idle.
- **Лог Bluetooth** заполнял CPU (0 % простоя) и подвешивал интерфейс. Логи на устройстве проверять на объём.
- **Яндекс lossless** требует `encraw` (не `raw`) и AES-256-расшифровку.
- **Клавиатура в скрытом слое** считалась показанной, и мини-плеер пропадал навсегда.
- **Статусбар:** значок ▶ / ❚❚ был инвертирован относительно кнопки мини-плеера.
